# The Silicon Gazette



The Silicon Gazette is an AI-written daily tech newspaper. Every day it searches the web for AI, tech and open-source news, has a language model write one edition from those results, stores it, and publishes it as an editorial broadsheet you can read, search and share.

## Stack

- **Framework:** Next.js 15.5 (App Router), React 19, TypeScript
- **Styling:** Tailwind CSS with a small token layer; fonts self-hosted through `next/font` (Instrument Serif, Newsreader, Geist, Geist Mono)
- **Motion:** GSAP 3 (ScrollTrigger) and Lenis smooth scrolling, both off under `prefers-reduced-motion`
- **Writing:** Groq `openai/gpt-oss-120b` (low reasoning effort), with Gemini `gemini-3.6-flash` as the fallback
- **Search:** Tavily
- **Validation:** Zod; every generated edition is normalised and validated before it is stored
- **Database:** Neon Postgres through Drizzle ORM 0.45
- **Rate limiting and locking:** Upstash Redis (optional)

Editions contain one lead story, up to 12 further stories (fewer when the day has fewer distinct events), 3 to 5 trending repositories and a one-line market brief.

## Features

- `/gazette/YYYY-MM-DD`: the edition. Masthead, a live wire ticker, the lead story in full, sections laid out as a bento grid, the Repo Beat, and the market brief. Sticky section navigation keeps the URL hash in sync.
- `/gazette/YYYY-MM-DD/story/<slug>`: the story reader, with a text-size control, native share, source link and previous/next story.
- `/archive`: every edition, grouped by month, with live search and a category filter.
- `/latest`: redirects to the most recent printed edition.
- Command palette on every page: press `/` or `Ctrl/⌘ K`.
- Light theme by default, with a dark theme you can switch to (the choice is remembered).
- A PNG social card per edition and per story, a sitemap and robots.txt.
- `/analytics`: a private, owner-only traffic dashboard (see [Analytics](#analytics)).

## API

| Route | Purpose |
|---|---|
| `GET /api/gazette/[date]` | Read a stored edition. Never generates. |
| `POST /api/gazette/generate` | Generate an edition. Without `Authorization: Bearer $CRON_SECRET`, only today's edition can be generated, and requests are rate limited. |
| `GET /api/gazette/generate` | Vercel Cron entry point. Requires the secret when `CRON_SECRET` is set. |
| `POST /api/track` | Analytics ingestion from the site's own pages (see [Analytics](#analytics)). |
| `/api/analytics/*` | Dashboard data. Needs an analytics session, except `login`, the `session/leave` beacon and `rollup` (which needs `CRON_SECRET`). |

New editions are generated by GitHub Actions at 02:50 UTC, with Vercel Cron as a backup at 04:00 UTC. If neither has run yet, the first reader of the day triggers generation and sees a printing-press loading screen.

## Quick start

```powershell
cd frontend
npm install
```

Open http://localhost:3000. It redirects to today's edition.

## Environment

All variables are listed with comments in [`frontend/.env.example`](./frontend/.env.example):

- `GROQ_API_KEY`, `GROQ_API_KEYS` (optional extra keys), `GROQ_MODEL`, `GROQ_REASONING_EFFORT` (default `low`)
- `GEMINI_API_KEY`, `GEMINI_MODEL`: fallback provider
- `TAVILY_API_KEY`
- `DATABASE_URL`, `DATABASE_URL_UNPOOLED`: Neon. Without them the app uses an in-memory store.
- `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN`: rate limiting, the cross-instance generation lock, the daily budget and alert de-duplication. Anonymous generation **fails closed in production if Redis is unreachable**. Check the setup with `npx tsx scripts/verify-redis.ts`.
- `CRON_SECRET`: required in production for the scheduled jobs. Set the same value in Vercel **and** as a GitHub Actions secret.
- `NEXT_PUBLIC_BASE_URL`: the public site URL (on Vercel it falls back to the production domain).
- `GENERATION_DAILY_LIMIT` (default 6): spending cap, the most full pipeline runs per UTC day.
- `DB_TIMEOUT_MS`, `GROQ_TIMEOUT_MS`, `GROQ_SECTIONS_BUDGET_MS`, `GEMINI_FALLBACK_CUTOFF_MS`: timeouts that keep a run inside the 300 s function limit.
- `ALERT_WEBHOOK_URL`: Slack or Discord webhook for alerts (failed generation, budget exhausted, server errors, rate limiter down).
- `ANALYTICS_PASSWORD` (20+ random characters) and `ANALYTICS_SALT_SECRET` (`openssl rand -base64 32`): the `/analytics` login and the key for daily visitor hashes. Set both in Vercel for Production and Preview.
- `NEON_STORAGE_LIMIT_MB` (default 512, the Free plan): used by the dashboard's storage report, which warns at 80%.
- `NEXT_PUBLIC_ANALYTICS_DEV=1`: collect analytics under `npm run dev` (off by default).

## Analytics

`/analytics` is a private dashboard for the site owner: page views, visitor-days, sessions, read depth and completion, top editions and stories, referrers, countries, devices, interaction events and a funnel, search usage, generation requests, 404s, database size, a live "reading now" count and CSV export.

**Signing in.** One password (`ANALYTICS_PASSWORD`). There are no cookies: the session token lives in `sessionStorage` and is sent as `Authorization: Bearer`. Sessions are stored (hashed) in Upstash Redis, so the dashboard needs a working Upstash database and refuses logins when Redis is down. You are signed out after 20 minutes without activity (with a warning a minute before) or about 15 seconds after the tab closes; a refresh keeps you signed in. Logins are limited to 5 attempts per 15 minutes per IP. The page is `noindex`, blocked in `robots.txt`, and served with a nonce-based Content-Security-Policy (`middleware.ts`).

**Privacy.** What is collected, and what isn't:
- No cookies and no IP addresses are stored. Visitors are counted with a hash of IP + user agent keyed by a secret that changes every UTC day, so the same person can't be linked across days.
- Search text is never stored, only result counts.
- Visitors who send Do Not Track or Global Privacy Control, and known bots, are not recorded.
- Page paths are stored without query strings.
- Signing in also excludes your own browser; the login page has an "Exclude this browser" link for other browsers.
- Raw events are kept indefinitely in Neon.

**How data flows.** The browser batches events to `POST /api/track` (a 4 KB and 10-event limit, and 120 requests a minute per IP). A nightly rollup at 00:20 UTC (GitHub Actions, `.github/workflows/analytics-rollup.yml`, with Vercel Cron at 02:00 UTC as a backup) aggregates yesterday into daily tables. The dashboard reads rollups for older days and raw events for the last 24–48 hours, using the same SQL for both, so the numbers match. Days are UTC; visitor and session counts are per day, summed over the range.

**Database schema.** `npx drizzle-kit push` creates the `events` and `daily_*` tables along with `editions` and `search_contexts` (each day's Tavily results, kept a week so a retry after a model failure doesn't search again).

**Backfill.** To rebuild rollups for past days, for example after an outage or a schema change, run the **Analytics Rollup** workflow manually with `from` and `to`, 400 days at most per run. Or call the endpoint directly:

```powershell
curl -X POST "$SITE_URL/api/analytics/rollup" -H "Authorization: Bearer $CRON_SECRET" -H "Content-Type: application/json" -d '{"from":"2026-09-01","to":"2026-09-30"}'
```

Rollups are idempotent, so running one twice gives the same rows.

**Checks.** `npm run verify:analytics` (in `frontend/`) tests visitor hashing, bot filtering, event validation, the session rules against the real Redis, and that every dashboard route requires a session. Add `-- --db YYYY-MM-DD` to also check rollup idempotency and rollup = raw for that day. This writes that day's rollup rows, just as the nightly job would.

## Monitoring

- **Logs:** one JSON object per line (`event`, `level`, fields), searchable in Vercel's logs. The "Reference" number readers see on an error page is the `digest` in the matching `request.error` line.
- **Alerts:** set `ALERT_WEBHOOK_URL`. Each distinct alert is sent at most once every 30 minutes.
- **Uptime:** point a monitor (UptimeRobot, Better Stack…) at `/api/health`. It returns 503 when the database or Redis is down, or when today's edition is still missing after 05:00 UTC.
- **Cron:** the GitHub workflow checks `/api/health` after generating, so a failed day fails the run and GitHub emails you. Set the repository variable `SITE_URL` if you use a custom domain.
